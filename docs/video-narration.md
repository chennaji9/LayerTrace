同时提供 `LayerTrace-narration.wav` 和 `LayerTrace-subtitles.srt`。如需换成自己的声音，按 [视频配音与导出操作](video-editing-guide.md) 操作。下表文字与成片旁白一致，时间码和操作说明不用朗读。

## 实际终端操作

提交视频回看已经完成的真实实验。需要补充独立实时实验镜头时，先执行 UI 指南第3、4节的准备步骤，再从 `UI-records-quick-guide.md` 复制实际参数对应的本机 WSL 编排命令。CPU 场景命令如下：

```bash
cd /mnt/d/ZSvirt/layertrace-runtime
python3 run-real-fault-r4.py cpu-quota \
  --cpus 0.1 --seconds 180 --during-count 1 \
  --number "${LT_NEW_EXPERIMENT_NUMBER:?按快捷表填写新实验编号}"
```

进程场景使用显式策略 `native-stop-before-client`。从所选 manifest / 快捷表读取秒数、请求数及新实验编号，分别赋给以下变量；该策略的准备参数为45秒、3个串行请求、间隔2秒：

```bash
python3 run-real-fault-r4-process-native.py process-failure \
  --process-injection-strategy native-stop-before-client \
  --seconds "${LT_PROCESS_SECONDS:?请先按真实记录填写进程故障秒数}" \
  --during-count "${LT_PROCESS_DURING_COUNT:?请先按真实记录填写串行请求数}" \
  --number "${LT_NEW_EXPERIMENT_NUMBER:?按快捷表填写新实验编号}"
```

编排器每次安排一个独立客户端；多个请求由该客户端严格串行发送。CPU 与工具场景先核验故障实际生效，再启动请求。进程场景的唯一原始客户端先导入原 `run_client_task`，输出 READY 后等待 stdin，预热阶段不发送 healthz 或业务请求；原生停止 Agent 后，确认恢复 watchdog 就绪、同一完整容器 ID / 启动代次已退出且退出码非零，再通过 stdin 放行原函数的3个请求。`client_process_started_at` 与 READY 时间单独保留，`client_launched_at` 表示业务放行时间。按 READY、原生停止确认、放行和请求终结原件核对顺序，验收范围为真实退出、停机业务不可达或失败及 R0 链恢复。

另一个受支持策略 `active-model-before-kill` 先发业务请求，经公开模型阶段守卫后停止 Agent；采用时单独保留守卫观察任务的真实结果和对应守卫原件。两种策略分别按所选 manifest 读取，计算中断需另外的直接证据。不要提前启动另一条请求流。新实验编号只标记独立记录，不推定通过次数。实时镜头的 run / task / incident 必须使用新实验实际记录。正常业务与必要的独立恢复命令在 guest `/opt/layertrace` 执行；完整六文件 Compose 合并入口见 UI 指南，不打印整份私有 env。

移机部署先按资产清单核对四份镜像 tar 与 cp、probe、workload、client manifests，再使用项目原生 `python3 -m scenarios.real_lab` 故障入口。本机编排器依赖现有 runtime、SSH 和数据库配置；材料中的冻结 runner 用于审阅编排和验收证据。独立客户端镜像与导入步骤见 [独立镜像与导入说明](client-image.md)。

## 镜头与配音核对

1. 每个实验的run ID、task ID、incident ID、诊断记录编号与交付证据一致，来源为真实观测。独立客户端记录task ID，故障CLI输出run ID，两者按时间与资源核对。录像使用固定 `revision` 的历史诊断，不能默认展示最新低支持记录却称为高支持。
2. 证据展开后留足阅读时间，HTTP503、CPU配额、节流、原始引用与来源标识可读。支持等级表示证据充分程度，不称数学概率。
3. CPU诊断按实际数值和缺失项解释。独立健康批次的成功样本数、任务内模型累计耗时 P95 和任务总耗时 P95 从最终 summary 及其 SHA256 绑定的批次汇总读取；R2预检滚动模型基线读取 `baseline.service_baseline_preflight`，正式诊断再按其保存时刻核对。模型累计字段是任务内initial与synthesis累计，不是单阶段P95；R2可逐条用闭合phase的真实duration_ms作累计量保守下界，不跨phase或task求和，关联窗口150秒。工作负载页是相关服务的任务总耗时口径。口播不朗读固定P95，字幕与快捷表按最终事实填写。最高单条耗时不称P95，35次请求不等于35次成功，失败/超时不计入健康样本。
4. 本次控制面恢复稳定窗口为15秒，项目默认60秒。实时录制的等待可剪辑，但字幕注明真实等待及前后时间；不能剪成即时恢复。
5. 确认按钮仅出现在待处理事件单。最终回看若选择已恢复记录，说明当前没有确认按钮；指纹静默针对后续匹配通知，不声称已经压制本次活跃告警。独立确认素材须保留真实对象和时间，并说明点击时事件单仍为待处理；事件单状态与物理故障生效状态分别核对。
6. 若增加平台管理界面镜头，隐藏令牌、密码与会话，业务VM UUID保持可核查。GPU/CUDA和R1/R4镜头明确标为回放或回归验证。
7. 提交主片为270秒中文配音视频，含同步字幕；逐段核对旁白、画面和字幕，确认可播放且关键证据可读。公开仓库和视频链接以实际匿名访问核验为准。
8. 页面入口使用真实按钮和链接：任务“详情” → “关联诊断”区域的“事件单 ××××” → 证据卡片摘要 → 卡片末尾“资源”链接 → 浏览器后退 → “返回事件单”。“确认”仅在待处理行显示；静默表单中填“演示用户”、5分钟，再按实际状态演示提交。
9. 进程镜头使用独立审计确认的停机失败 task，逐条核对 READY、原生停止确认、业务放行、失败与恢复时刻。采用 `active-model-before-kill` 时另保留守卫观察任务的实际结果；公开 `running` 观察和停机后失败均不能单独证明在途模型计算被中断。


时间记录核对：虚拟机中的停止、业务放行回执和恢复时间属于同一时钟；WSL 中的命令发送与接收时间单独排序。两台机器可能存在时钟偏差，不直接用跨主机时间差推定先后；放行还须通过单调时钟期限、同一身份回执和虚拟机内截止时间检查。

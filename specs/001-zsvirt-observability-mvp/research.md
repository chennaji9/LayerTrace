# Phase 0 研究结论：ZSvirt 全栈可观测诊断 MVP

本文固化 `docs/ZSvirt-MVP设计方案.md` v3 中已经完成的技术取舍，并补充实施所需边界。
所有技术上下文均已决策，不存在未决澄清项。

## 1. 总体架构

**决策**：采用模块化单体控制面、一个独立 worker、每台目标 VM 一个探针，以及可替换的平台、
运行时和证据查询适配器。

**理由**：个人开发周期只有约 21 至 29 个工作日；模块化单体可以在进程内保持事务和调试简单，
独立 worker 又能避免多个 Web worker 重复轮询。适配器与版本化契约保留后续扩展空间。

**考虑过的替代方案**：微服务、消息队列、事务 outbox、多 worker 租约。首版吞吐和团队规模
不需要这些复杂度；只有队列积压经基准测试持续超标时再升级。

## 2. 控制面语言与框架

**决策**：使用 Python 3.11+、FastAPI、Pydantic、SQLAlchemy 和 Alembic；后台任务复用同一领域
代码，由单独 worker 进程执行。

**理由**：Python 对采集适配、数据校验、规则实现和本地 AI 样例均有成熟生态；类型化契约和迁移
工具能降低跨模块数据漂移风险。

**考虑过的替代方案**：Go 可降低探针开销但会增加双语言契约和个人实施成本；Django 自带能力较多，
但当前 API、异步采集和轻量页面需求不需要其完整框架。

## 3. Web 界面

**决策**：使用 Jinja2 服务端模板、HTMX 局部更新、Cytoscape.js 拓扑和 ECharts 图表；浏览器资源
锁定版本并存入 `static/vendor`，不引入 Node 构建步骤。

**理由**：方案要求先点亮 8 个工作页面并在每轮展示变化，服务端渲染能让一人团队快速交付，
同时通过专业图形库满足拓扑和指标可视化。

**考虑过的替代方案**：React/Vue 单页应用会增加构建、状态同步和两套模型成本；纯静态页面无法
满足局部刷新、拓扑交互和事件单操作。

## 4. 事实与元数据存储

**决策**：PostgreSQL 保存资源、别名、时态关系、事件、任务、告警、事件单、静默、诊断和快照；
使用唯一约束、事务、JSONB 和迁移管理。

**理由**：首版需要幂等、事务一致性、有效期查询和半结构化扩展字段，而规模不足以证明引入
图数据库或额外事件存储的价值。

**考虑过的替代方案**：图数据库增加部署与查询模型复杂度；SQLite 不适合多进程 worker、并发写入
和目标部署；把时序样本写入 PostgreSQL 会混淆存储边界并放大数据量。

## 5. 指标与链路存储

**决策**：Prometheus 保存数值指标并负责持续阈值判断；Tempo 只在标准档启用时保存 Span；
Grafana 用于原始指标和链路深链，不作为产品状态事实来源。

**理由**：复用成熟开源后端可集中精力实现资源关联、诊断和证据呈现；查询适配层避免 PromQL
散落到规则代码中。

**考虑过的替代方案**：自建时序存储、把全部日志与 Span 放入 PostgreSQL、首版强制 Tempo。
这些选择都会增加实现或运行成本，且 Tempo 已列入止损优先项。

## 6. 指标数据通路

**决策**：默认由中心 Prometheus 每 10 秒抓取 node_exporter 与探针指标；迭代 0 若确认中心无法
访问 VM，则改为 VM 内 Prometheus agent 经认证且加密的入口 remote write。所有跨主机抓取和
remote write 都必须验证 TLS 对端身份，两种方向必须产生相同标签。

**理由**：pull 路径组件更少且便于目标健康检查；remote write 仅作为只允许 VM 出站网络的明确降级。

**考虑过的替代方案**：探针直接 remote write 作为唯一方案会增加认证与缓存调试面；开放公网抓取
端口违反安全边界。

## 7. 事件数据通路与可靠性

**决策**：平台适配器、探针和应用 SDK 通过批量事件 API 写入；重要事件先进入探针的有界 spool，
控制面按 `event_id` 幂等入库。spool 初始上限取 100 MiB 或 10 分钟，先到者为准。契约限制单条
事件序列化大小为 256 KiB，单批请求为 8 MiB 或 500 条，顶层属性为 64 项，嵌套深度为 8 层；
任一限制超出时整批在入队前拒绝并返回 413，不进行静默截断。

**理由**：业务事件频率远低于指标，但身份、任务开始和故障事件不能因短时断网轻易丢失；有界缓存
可以明确控制资源，并通过 `dropped_count`、gap 和 `queue_lag` 诚实暴露损失。

**考虑过的替代方案**：Kafka 和无限本地队列超出 MVP；同步阻塞业务直到中心确认会放大故障影响；
“保证零丢失”在容量耗尽与进程崩溃条件下不可验证。

## 8. 身份与历史拓扑

**决策**：资源唯一键为 `(tenant_id, provider, provider_instance, kind, source_id)`；跨源身份只能通过
带命名空间和有效期的显式别名合并。关系保存 `valid_from/valid_to`，重建或迁移关闭旧关系。

**理由**：主机名、IP 和显示名会复用；诊断必须引用故障时刻的实例与拓扑才能长期可解释。

**考虑过的替代方案**：名称/IP 模糊合并只能生成待确认建议；完整通用双时间数据库超出首版，
首版只在明确生命周期事件发生时关闭关系。

## 9. 诊断引擎

**决策**：规则元数据使用无可执行代码的 YAML，复杂判断由受测试的 Python evaluator 注册；处理顺序为
标准化、身份解析、上下文构建、候选评估、影响判断和版本化输出。首版实现 R1 至 R4。

**理由**：声明式窗口、阈值、关系路径和建议便于审阅；复杂反证逻辑保留在可测试代码中。禁止配置
执行任意 Python 或 SQL 可以缩小安全面。

**考虑过的替代方案**：纯 YAML 表达不了复杂反证；全部硬编码难以版本化和展示规则参数；用大模型
直接判根因不满足证据可重复和离线要求。

## 10. 延迟基线与规则时间参数

**决策**：R2 与 R4 共用一个基线服务：最近 15 分钟排除已有事件单时段后的请求延迟 P95；最近
1 分钟 P95 超过基线两倍且绝对增加超过 500 ms 才判升高；样本少于 30 条时输出“基线不足”。
Agent 超时初值也由该服务提供，取基线 P95 的三倍。窗口、样本数、值和判据存入规则版本并在
诊断中展示，禁止各 evaluator 或 Agent 复制一套计算逻辑。

**理由**：CPU 推理绝对延迟差异大，相对且带绝对门槛的判据比固定阈值稳定；展示当时参数才能复现。

**考虑过的替代方案**：固定毫秒阈值无法适应模型和硬件差异；样本不足时强行判断会产生虚假诊断。

## 11. 告警与事件单事实边界

**决策**：控制面每 15 秒读取 Prometheus 告警状态并结合事件规则生成 Alert；控制面按项目、规则和
稳定故障对象形成指纹并独占 Incident 生命周期。外部 Alertmanager/Webhook 只接收通知。

**理由**：单一事实来源能避免控制面、Prometheus 和通知系统三方状态冲突；静默只影响通知而不隐藏事实。

**考虑过的替代方案**：从 Alertmanager 回调反向创建事件单会形成双向一致性问题；每个任务单独建
事件单会造成告警风暴。

## 12. VM 探针分档

**决策**：轻量档为 probe + node_exporter，标准档额外加入 OpenTelemetry Collector；探针负责注册、
心跳、Docker 发现/事件、限制快照、容器指标和事件转发。Docker API 通过受限代理访问。

**理由**：分档允许在 Agent Span 完整性和资源开销之间按环境选择；受限代理避免把只读 socket
挂载误当作权限隔离。

**考虑过的替代方案**：默认 privileged 或直接暴露 Docker socket 风险过高；强制 Collector 会使
轻量部署无法证明低侵入目标；cAdvisor 在现有 Docker/WSL 实验中尚未可靠运行。

## 13. ZSvirt 集成

**决策**：迭代 0 先运行只读 preflight，记录实际平台指标/告警字段、VM CPU 上限、guest steal、
中心到 VM 的网络方向、TLS 入口和权限结果；在记录完成前不得选择 pull/remote write 或实现字段
映射。随后实现只读 `ZSvirtProvider`，启动时报告能力并支持增量资源、关系、事件及可用指标；
增量游标与批次同事务提交，无游标接口使用重叠窗口加去重。缺失能力在 `/status` 中显式展示。

**理由**：官方接口能力尚未在仓库中固化，能力发现与诚实降级可以在不伪造字段的前提下继续实施。

**考虑过的替代方案**：申请管理员权限或假设固定字段违反最小权限与诚实降级；平台断开时删除资源
会把接口失败误判为真实消失。

## 14. 回放与样例工作负载

**决策**：`ReplayProvider` 与 ZSvirtProvider 输出同一内部结构；剧本只含原始事实和测试期望，
期望永不进入页面。样例工作负载使用许可允许的 CPU 小型开放权重模型和 llama.cpp server，
Agent 固定执行“模型调用 -> 工具调用 -> 汇总”。

**理由**：同管线回放才能验证真实规则而不是播放答案；固定流程和本地模型消除网络与随机输出对
故障实验的影响。

**考虑过的替代方案**：外部闭源 API 不满足离线与许可要求；模拟模型调用无法证明 AI 工作负载；
测试生成文本内容会引入不稳定断言。

## 15. 测试与交付策略

**决策**：使用 pytest 覆盖领域规则、契约、迁移和集成；Docker Compose 驱动真实场景；Playwright
覆盖 8 个页面、来源徽标、操作流程和截图。每条诊断规则至少有一个正例和一个混淆反例。

**理由**：宪章要求可见增量和自动验证并存；浏览器测试证明用户工作流，规则反例防止错误归因，
干净环境 quickstart 证明可复现性。

**考虑过的替代方案**：只做单元测试无法验证数据通路和 UI；只做手工演示无法稳定回归；固定样例
正确率不能外推为通用根因准确率。

## 16. GPU 与可选组件

**决策**：无 GPU 时提供带 `replayed` 来源、可信设备映射和直接 CUDA OOM 错误证据的正向回放，
并保留“只有高利用率不得归因”的反例；有物理 GPU 时仅在取得 UUID、显存、进程和直接 CUDA
错误证据后验证；vGPU 必须取得可信映射，否则宿主机归属显示未知。Tempo、通知、D2/D3 均按
能力启用并服从第 15 个工作日止损规则。

**理由**：高利用率不是故障证据，且平台能力不可预设；把可选项从必需闭环剥离可以保护交付进度。

**考虑过的替代方案**：仅凭 GPU 利用率归因、把 D2/D3 设为必需、提前实现自动修复，均会违反证据
原则或扩大不可控依赖。

## 17. 跨主机传输安全与许可证准入

**决策**：使用固定版本 Caddy 统一终止控制面跨主机入站 HTTPS；node_exporter 使用自身 TLS Web
配置保护 Prometheus pull；平台适配器验证 ZSvirt 上游证书。探针、Prometheus、浏览器和平台适配器
都必须验证受信 CA、主机名和有效期，明文及不可信证书连接被拒绝。证书以挂载文件提供并支持不中断
已提交事件的轮换。同一主机的 loopback 开发和回放入口可绕过 Caddy 使用 HTTP。第三方前端资产、
镜像和模型在首次引入前必须通过许可证 allowlist 与再分发兼容性检查，发布前再做全量复核。

**理由**：认证令牌不能防止跨主机窃听；集中 TLS 入口能减少证书配置分叉。许可证前置门禁避免在
交付末期才发现模型或静态资产不可分发。

**考虑过的替代方案**：每个进程分别终止 TLS 会复制证书和轮换逻辑；仅依赖隔离网络或 VPN 无法
作为所有评审环境都具备的前提；只在发布阶段审查许可证会放大替换成本。
